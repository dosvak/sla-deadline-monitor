# SLA Deadline Monitor (SLAMON) - process application

One dashboard that shows every open task of the server (or of one application) in lateness buckets - overdue more than 24 h, 1 to 24 h, less than 1 h, due soon, on time, no due date - with reassignment of the selected tasks to a user or a group and a CSV export. The Summary tab counts the buckets. 1.1 adds the **Aging** report (open tasks by age since received - under 1 day, 1 to 3, 3 to 7, over 7 days - per team / person and application, or per application only) for capacity planning, and the **At risk** watch list (tasks the engine marks at risk through `taskIsAtRisk` / `taskAtRiskTime`) as the escalation view.

Package `SLA-Deadline-Monitor-1.1.twx` (generated by `tools/build_slamon.py` on twxkit + kitlib, standard library only, no base export); targets: 8.6.2, BAW 24-26 (classic v1 API); CP4BA with the /bas prefix in serverBaseURL.
Vanilla BAW: UI Toolkit controls only, one client-side human service, server-side service flows calling the REST API with the technical
user of the environment variables. Import through the Process Center / Workflow Center console (`pc_import.py`) or Studio, set the
environment variables of the snapshot, open the dashboard from Process Portal or the playback URL of the `.ids.json`.

## Dashboard

| Tab | Content |
|---|---|
| Tasks | criteria (application acronym, bucket, max rows), Refresh, Reassign selected (modal: user login or group name), Export CSV; multi-select table of the open tasks |
| Summary | tasks per bucket |
| Aging | application, group by team / person or application, Aging report; table with the four age buckets, total and oldest |
| At risk | application, At-risk tasks; table task / assigned to / at risk since / due / priority / instance / process / application |

Every list has a status line; errors open a message modal; CSV export shows the text in a modal for copy / paste.

## Service flows and REST calls

| Flow | Does |
|---|---|
| SL Init | environment variables + current user -> header |
| SL List Tasks | `PUT /search/query?organization=byTask&columns=taskId,taskSubject,taskActivityName,taskPriority,taskDueDate,taskReceivedDate,assignedToUser,assignedToRoleDisplayName,instanceId,instanceName,bpdName,instanceProcessApp&condition=taskStatus|Equals|New_or_Received[&condition=instanceProcessApp|Equals|<acr>]&sort=taskDueDate&size=500` -> buckets computed server side from `taskDueDate` against now |
| SL Reassign | `PUT /task/{id}?action=assign&toUser=<login>` or `&toGroup=<group>` per selected task; counts done / failed, first three error texts |
| SL Rows To CSV | rows -> CSV text (modal) |
| SL Aging | open tasks (byTask) bucketed by `taskReceivedDate` age per `assignedToUser` / team and application |
| SL At Risk | open tasks with `taskIsAtRisk` true, `taskAtRiskTime` |

## Environment variables

`serverBaseURL`, `restAuthUser`, `restAuthPassword`, `restTrustAllCertificates` (kit-rest.js: the technical user every server-side flow calls the REST API with), `appTitle`, `slaWarnHours` (due-soon window, default 4).

## Business objects

SLQuery (application, bucket, maxRows), SLRow (bucket, hours, taskId, subject, activity, assignedTo, priority, dueDate, received, instanceId, instanceName, bpdName, app), SLCount, SLResult (rows, counts), SLAssign (taskIds comma list, toUser, toGroup), SLActionResult.

## Build, test, verify

```
python3 tools/build_slamon.py --snapshot 1.1                       # -> SLA-Deadline-Monitor-1.0.twx + .ids.json
KITENV_serverBaseURL=https://<host>:9443 KITENV_restAuthUser=<user> KITENV_restAuthPassword=<pw> \
  python3 tools/build_slamon.py --snapshot 1.0-lab                 # lab build with real defaults (a snapshot caches tw.env: new name)
python3 tools/pc_import.py SLA-Deadline-Monitor-1.1-lab.twx
python3 tools/kit_flow_test.py SLA-Deadline-Monitor-1.1-lab.ids.json "<flow>" '{"data": {...}}'   # every flow over REST
python3 tools/dash_test.py <host> <branch> <cshs>             # playback: tabs, JS errors, failed calls
```

Verified: 8.6.2.20001 lab: 34 open tasks read and bucketed (all overdue); reassignment of task 955 to a user, back to its team with `back=true`; an unknown login answers 404 `AssignActionFetchErrorException` and is reported per task. 1.1: aging report of 34 tasks in 9 team / application groups (4 per application), 34 at-risk tasks listed. Dashboard playback of 1.0 and 1.1: no JavaScript error, no failed call.

## Pitfalls met

* `taskAssignedTo` is not a search column (CWTBG0037E) although it appears in the rows; use `assignedToUser` / `assignedToRoleDisplayName`.
* The engine sorts ascending only; the lateness order is computed server side.
* Team tasks show as `team: <name>`; reassigning a team task to a user takes it from the team (return it with the Workload Balancer or `action=assign&back=true`).
